실험 원본은 사용자의 데스크톱 PC에 있습니다. 원격은 비공개 GitHub 저장소이고, 커밋하지 않은 데이터는 원격에 없습니다. 다른 기기에서 run.py를 실행하지 마세요. 사용자가 그 기기로 실행 위치를 옮긴다고 직접 말한 경우만 예외입니다. 데이터 폴더 하나에는 프로세스 하나만 써야 합니다.

지금 어디까지 왔나

Sonnet, Opus, Fable 세 모델이 가산 조합론 미해결 문제를 만들고, 풀고, 평가합니다. 지금 돌고 있는 프로세스는 없습니다. Fable 주간 한도는 11-10 23시 기준 42%, 전체 한도는 54% 사용했고 2026-11-14 07:00 KST에 초기화됩니다. 실험 마감은 2026-11-17입니다.

다음에 할 일

11월 7일 예약 실행(aa9771d9)은 사라졌습니다. 이제 실행은 데스크톱에서 프로젝트 루트 C:\Users\user\Desktop\학자연으로 가서 사람이 지켜보며 시작합니다. 아래 명령은 사전 지정 문서(docs/preregistration_2026-11-11.md)를 커밋한 뒤에만 실행합니다. 먼저 로그인 상태, 중복 run.py가 없는지, Fable 한도(멈춤선 90%, 전체 85%)를 확인합니다. 11월 10일 승인된 순서는 고컨텍스트 출제가 먼저이고, 그다음 H-P3를 가르는 4칸입니다.

python run.py --data-dir high_ctx2/data gen --context context/additive_comb_high_v2.md --kind open --n 3
python run.py --models fable solve --only P-5d88c3,P-e1102e,P-09b1eb,P-fd59f2

사람 평가는 고컨텍스트 풀이를 기다리지 않고 11월 12일 정오에 문제만 내보냅니다. 11월 14일 07:00 한도 초기화 뒤에는 남은 Fable 문제 평가, 고컨텍스트 풀이, P-cbca09, 체커 검증, Sonnet과 Opus의 새 풀이 평가, Fable의 풀이 평가 순으로 돌립니다. --only 없이 solve를 돌리면 닫은 P-c2d5cd가 다시 시도되므로, 남은 Fable 풀이는 문제를 지정해 돌립니다. 정확한 옵션은 python run.py --help로 확인합니다.

아래 명령은 이 순서를 따릅니다. eval은 문제를 먼저, 풀이를 나중에 평가하고, 문제만 평가하는 옵션은 없습니다. 그래서 첫 줄은 문제 평가가 끝나면 멈추고, Fable의 풀이 평가는 맨 끝에서 다시 돌립니다. 고컨텍스트 폴더는 풀이 전에 평가하면 문제만 평가됩니다.

python run.py --models fable eval
python run.py --data-dir high_ctx2/data --models fable eval
python run.py --data-dir high_ctx2/data --models sonnet,opus solve
python run.py --data-dir high_ctx2/data --models fable solve
python run.py --models fable solve --only P-cbca09
python run.py verify
python run.py --models sonnet,opus eval
python run.py --data-dir high_ctx2/data --models sonnet,opus eval
python run.py --models fable eval
python run.py --data-dir high_ctx2/data --models fable eval

한도가 모자라면 자르는 순서는 ① P-c2d5cd ② P-cbca09 ③ Fable의 풀이 평가 ④ 고컨텍스트 Fable 풀이입니다. 끝까지 지키는 것은 고컨텍스트 출제, H-P3 4칸, Fable의 문제 평가 40건입니다. 내보내기 준비가 끝나기 전에 전체 한도가 75%에 닿으면 Fable을 멈추고 4칸을 11월 14일 07:10으로 넘깁니다. Fable 평가 처음 3건의 실제 비용 평균이 건당 0.5달러를 넘으면 Fable의 풀이 평가는 처음부터 뺍니다. 사용량 한도로 멈추면 초기화 뒤 같은 명령을 다시 실행합니다. 끝난 항목은 건너뜁니다. 그다음 순서는 다음과 같습니다.

  1. 데이터를 커밋하고 진행판을 갱신한 뒤 python analyze.py를 실행합니다.
  2. 발표 덱 수치를 갱신합니다. 출력 상한을 "Fable만 절반"이라고 쓴 슬라이드(limits)도 고칩니다.
  3. 사용자가 교수 두세 분께 이메일로 부탁합니다. 1순위는 연세대 교수, 그다음은 서울 소재 다른 대학 교수입니다. 사람 평가 묶음은 결정 10을 기다립니다. 추천안은 문제 7개, 약 30분입니다.
  4. export-human을 한 번만 실행합니다. 다시 내보내면 평가자 진행이 초기화됩니다. 11월 12일 정오로 계획했고, 링크를 보낸 뒤에는 다시 내보내지 않는다는 해석은 결정 14로 남아 있습니다.
  5. eval_page/index.html을 아티팩트로 게시합니다. capabilities는 {db: {}, downloads: true}이고, 주소를 README 4절에 적습니다. 게시 뒤 로그아웃 상태에서 열리는지 확인합니다.
  6. 회수 마감(결정 13 대기, 추천 11월 16일 18:00) 뒤에 import-human과 최종 분석을 실행합니다. 분석 완료 목표일은 11월 17일입니다.

  • 등급 차이: 풍요로움의 Kruskal 검정은 p=0.78로 유의하지 않습니다.
  • 풀이: open 문제 성공은 0건입니다. 해결 주장 4건 가운데 체커를 통과한 2건은 같은 문제 P-d6bfbe이고, 나머지는 P-4c5a9d가 3점과 2점, P-5d88c3이 1점과 1점입니다.
  • 신규성: 유효 22문제 중 21개에서 같거나 가까운 질문이 문헌에 있었습니다. 문제당 검색 2~3회로 확인했고, 그중 15건은 변형 여부가 판단에 달려 있습니다.
  • AI 평가자: Sonnet은 문헌상 가까운 21문제 중 19개를 "알려지지 않음"이라 했고, Opus는 답한 생성 문제 15개를 전부 "알려짐"이라 했습니다. 출제 모델의 신규성 자신감은 판정과 무관하게 0.6~0.7입니다.
  • 외부 맥락: 이번 실험의 도구 없는 60분 단일 호출과 AI 준리만가설 증명의 수시간 에이전트 체제는 규모가 다릅니다. P3 결과를 능력 부재로 읽으면 안 됩니다.

인용 금지: 자기 평가를 뺀 난이도 p=0.035는 쓰지 마세요. 평가자가 둘뿐이라 출제 모델과 평가자 효과가 섞여 있습니다. 체커 통과 3건도 모두 한 문제에서 나왔으므로 등급 차이의 근거가 아닙니다.

사용자가 정한 것

  • 모델 역할: 계획은 Fable, 검증은 Opus, 구현은 Sonnet입니다. 다만 Fable 단계가 끝날 때까지 데스크톱 세션은 Opus로 두어 Fable 한도를 아낍니다. 대화 세션을 Fable로 두면 실험의 Fable 한도가 줄어듭니다.
  • 평가 블라인드: 평가자에게 why_important를 숨기고 평가를 시작했습니다.
  • 고컨텍스트 조건: 고컨텍스트 설계는 2026-11-06 사용자가 승인했습니다(설계서 §16). 팩 context/additive_comb_high_v2.md(논문 조사 세션이 만들고 사용자가 승인, 근거 docs/high_ctx/), 모델당 open 3개(줄기 1·2·3에서 하나씩), 풀이 27칸, AI 평가, 새 폴더 high_ctx2/data. 팩은 출제 때만 보여 줍니다. 11-10에 순서를 바꿨습니다. 고컨텍스트 출제가 맨 먼저이고, 풀이와 AI 평가는 한도가 허락할 때 뒤에 돌립니다. 사람 평가 내보내기는 export-human --extra-data-dir high_ctx2/data로 한 번입니다. 팩 텍스트는 고정입니다. 한 글자라도 바꾸면 생성이 처음부터 다시 돕니다.
  • 2026-11-10 결정: 마감은 11-17이고 사람 평가는 교수 두세 분께 이메일로 부탁합니다(연세대 교수 1순위, 그다음 서울 소재 다른 대학 교수). 사람 참여 연구 절차는 이미 승인받았습니다. 순서는 고컨텍스트 출제, H-P3 4칸이고, 사람 평가는 고컨텍스트 풀이를 기다리지 않고 11-12 정오에 문제만 내보냅니다. P-c2d5cd는 "제공자 안전 필터로 답을 얻지 못함"으로 닫고 결측으로 셉니다. 자르는 순서와 멈춤선은 위 "다음에 할 일"에 있습니다. H-P3 주 판정은 예산 초과를 실패로 세고, 예산 초과 칸을 결측으로 뺀 판정을 함께 싣습니다. P-d6bfbe는 H-P3 사례로 부르지 않습니다. 모델은 별칭이 아니라 정확한 이름(claude-sonnet-5-5, claude-opus-5-5, claude-fable-5-1)으로 부릅니다. 메일과 첫 화면에서는 "AI가 낸 문제와 사람이 낸 문제가 섞여 있고, 어느 쪽인지는 마감 뒤에 알려 드린다"까지만 밝힙니다.
  • 아직 정하지 않은 것: 결정 10~17입니다. 사람 평가 묶음 3단계, "검색 없이" 안내, 평가 끝 선택 질문, 회수 마감과 응답 처리, "내보내기 한 번" 규칙의 해석, H-P2 의미 있는 차이의 기준, 계획서 항목의 연기와 생략, 감사 표시입니다. 추천안은 docs/plan/2026-11-10-7day-plan.md에 있습니다.
  • 적용하지 않은 변경: 시간 제한 1800초, 예산 1회, 평가 effort 고정입니다. 실험 목적에 맞는 수정만 적용했습니다.
  • 풀이 배정 설계: 11-04에 평가자 섭외 후로 미뤘습니다. 11-10 계획은 문제 중심이라 이 항목은 결정 10으로 이어집니다.

실행할 때 알아 둘 것

  • 모델 호출: llm.py가 로그인된 Claude CLI를 헤드리스로 부릅니다. 호출당 제한은 3600초이고 도구는 끕니다. 11-10 결정에 따라 별칭 대신 정확한 모델 이름을 넘기도록 작업 트리의 llm.py를 고쳤고(커밋 전), 실행 창의 자동 업데이트는 끕니다. 실행 전에 로그인 상태를 확인합니다.
  • 중단 규칙: 연속 5회 실패하면 멈춥니다. 네트워크나 로그아웃이 원인이면 같은 명령을 다시 실행합니다.
  • 종료 코드 3221225794: Windows 로그아웃이나 종료로 CLI가 시작되지 못했다는 뜻입니다. 로그인 후 다시 실행합니다.
  • 알려진 한계: Fable은 한 번에 64,000토큰까지 쓰고, 잘리면 같은 호출 안에서 최대 3번 이어 써서 합계 256,000토큰과 60분까지 씁니다. Sonnet과 Opus는 한 번에 128,000토큰까지 쓰고, 한 호출에 쓴 양은 가장 많아야 166,750토큰이었습니다. 차이는 합계 분량이 아니라 Fable이 더 자주 끊긴다는 점입니다. 풀이 모델에게는 계산 도구가 없었습니다. effort는 CLI 기본값이고 기록되지 않습니다.
