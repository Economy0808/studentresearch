4. 8×3+9는 왜 그렇게 정했는가?

8은 모델 하나가 내는 문제 수로, open 5개와 checkable 3개입니다. 3은 모델 수입니다. 9는 사람이 낸 대조군입니다. 대조군을 넣는 것 자체는 계획서 2.2에 있는 설계입니다. 그러나 8과 9, 그리고 5 대 3이라는 숫자는 계획서에 없고 제가 정했습니다. 설계서에도 왜 이 숫자인지 근거를 적지 않았고, 비율을 따로 여쭌 기록도 없습니다.

5. checkable 15건은 6개 + Erdős 9개인가?

아닙니다. checkable은 모델당 3개씩 총 9개입니다. 그중 2개를 제외해 지금 유효한 것은 7개입니다. 대조군 Erdős 문제는 9개 모두 open이어서 checkable이 하나도 없습니다. 데이터에서 15에 맞는 수는 모델이 낸 open 문제 수인 5×3입니다. 또한 문헌 대조에서 "가까운 변형이 있음" 판정도 15건이어서, 15라는 숫자가 다른 뜻으로 섞였을 수 있습니다.

표에 자주 나오는 말 세 가지

  • 등차수열: 간격이 일정한 수의 나열입니다. 3, 7, 11이 그 예입니다. 많은 문제가 "등차수열이 생기지 않게 수를 최대한 많이 고르면 몇 개까지 가능한가"를 묻습니다.

  • 기저: 그 집합의 수 몇 개를 더하면 충분히 큰 정수를 전부 만들 수 있는 집합입니다. 동전 몇 종류로 모든 금액을 만드는 것과 비슷합니다.

open 문제와 checkable 문제

모델은 두 종류의 문제를 냅니다. 차이는 답이 맞는지를 어떻게 확인하느냐에 있습니다.

open 문제: 사람이 읽고 판단해야 하는 문제

"이런 성질이 항상 성립하는가?"처럼 일반적인 형태로 묻는 문제입니다. 답은 긴 증명 글이 됩니다. 컴퓨터로 맞고 틀림을 바로 판정할 수 없어서 평가자가 읽고 점수를 줍니다. 논문을 심사하는 일에 가깝습니다.

실제 예시: P-0ec34a (Opus가 낸 open 문제)

For $N\in\mathbb N$ let $R(N)$ be the largest size of a set $A\subseteq[N]$ that contains no triple $x,\ x+d^2,\ x+2d^2$ with $x\in\mathbb Z$ and $d\in\mathbb N$, i.e. no $3$-term arithmetic progression whose common difference is a nonzero perfect square. Is it true that $R(N)\ll_C N/(\log N)^C$ for every $C>0$? More strongly, is there an absolute constant $c>0$ such that $R(N)\le N\exp(-(\log N)^c)$ for all large $N$?

기호를 몰라도 괜찮습니다. 간격이 제곱수인 등차수열을 피해서 수를 고를 때 얼마나 많이 고를 수 있는지 묻는 문제입니다. 답을 자동으로 검사할 방법은 없습니다.

checkable 문제: 컴퓨터가 채점할 수 있는 문제

일반적인 문제에 더해, 숫자를 구체적으로 정한 작은 퍼즐을 함께 내게 합니다. 이 문서에서는 이 작은 퍼즐을 "유한판"이라고 부릅니다. 모델은 세 가지를 함께 제출합니다.

  • 일반 문제: open과 같은 형태의 진술입니다.
  • 유한판: 숫자를 고정한 퍼즐입니다. 답은 숫자 목록처럼 구체적인 물건입니다.
  • 체커: 제출된 답이 유한판의 조건을 만족하는지 검사하는 파이썬 코드입니다. 문제를 낸 모델이 직접 씁니다.

풀이 모델은 답을 숫자 목록으로 내고, 체커가 맞으면 통과, 틀리면 실패로 판정합니다. 자동 채점 시험과 비슷합니다.

실제 예시: P-d6bfbe (Sonnet이 낸 checkable 문제)

Let $r_3(N)$ be the largest size of a subset of $[N]=\{1,\dots,N\}$ containing no non-trivial 3-term arithmetic progression. Kelley–Meka give $r_3(N)\le N\exp(-c(\log N)^{\beta})$, while Behrend's construction gives $r_3(N)\ge N\exp(-C\sqrt{\log N})$. Problem: construct, for infinitely many $N$, a 3-AP-free set $A\subseteq[N]$ with $|A|\ge N\exp(-o(\sqrt{\log N}))$, i.e. beat Behrend's exponent $\sqrt{\log N}$ asymptotically (or prove that no such set exists for large $N$ by improving the upper bound to $N\exp(-c\sqrt{\log N})$).

유한판

Find a subset $A\subseteq\{1,\dots,200\}$ with $|A|\ge 37$ containing no non-trivial 3-term arithmetic progression (no distinct $x<y<z$ in $A$ with $x+z=2y$).

제출 형식

a JSON array of at least 37 distinct integers in the range 1..200

쉽게 말하면 유한판은 "1부터 200까지에서, 3항 등차수열이 생기지 않게 37개 이상 골라라"입니다. 일반 문제는 훨씬 어려운 질문으로, 문헌 대조에서도 아직 열려 있는 문제로 나왔습니다.

왜 두 종류로 나누었나

P3를 재려면 "하위 모델은 못 풀고 상위 모델은 푸는" 문제가 필요합니다. 그런데 진짜 난제만 있으면 세 모델이 전부 못 풀어서 모든 성공률이 0이 되고, 등급 차이를 볼 수 없습니다. 그래서 등급 차이가 드러날 만한 난이도의 문제가 필요했습니다. 계획서 2.2도 "생성 문제의 일부를 기계로 확인 가능한 형태로 한정한다"고 썼습니다. open은 주로 P2와 P4에, checkable은 주로 P3에 쓰입니다. 계획서의 Lean 4 형식 증명은 Lean을 설치하지 않아 빠졌습니다.

checkable의 한계 두 가지

  • 유한판을 풀어도 일반 문제가 풀린 것은 아닙니다. 위 예시에서 세 모델의 답이 모두 체커를 통과했지만, 일반 문제는 그대로 열려 있습니다. 유한판이 너무 쉬웠던 것입니다.
  • 문제를 낸 모델이 체커까지 씁니다. 체커가 틀렸거나 유한판에 답이 아예 없을 수 있습니다. 실제로 2개가 답이 없는 문제였습니다. 그래서 체커 검토 단계를 두었습니다.

초점이란 무엇인가

모델은 팩 전체를 읽지만, 프롬프트는 호출마다 "이 절의 빈틈에서 문제를 내라"고 절 하나를 지정합니다. 이것이 초점입니다. 첫 번째 호출은 첫 번째 결과를, 두 번째 호출은 두 번째 결과를 받습니다.

open은 5번 호출하므로 앞의 5개 절이, checkable은 3번 호출하므로 앞의 3개 절이 쓰였습니다. 그 결과 뒤의 4개 절은 초점으로 쓰인 적이 없습니다. 또 세 모델이 같은 절에서 문제를 내므로 비슷한 문제가 반복됩니다. 등차수열 관련 문제가 많은 이유입니다. 모델끼리 비교하기에는 공정하지만, 분야를 고르게 다루지는 못합니다. 코드 구조에서 나온 결과이고 제가 미리 말씀드리지 않았습니다.

프롬프트 원문은 prompts/gen_open.md와 prompts/gen_checkable.md에 있습니다. 모델이 낸 문제 전체는 생성된 문제 열람에서 수식으로 볼 수 있습니다.

실행 규칙과 그 이유

  • 호출당 60분: 처음에는 30분이었는데 Fable이 자주 시간을 넘겨서 10월 29일에 모든 모델을 60분으로 늘렸습니다. 30분 규칙의 시간 초과 기록은 지우고 그 칸을 다시 풀었습니다.
  • 예산 규칙: 한 칸이 시간 초과나 출력 길이 초과로 2번 실패하면 더 시도하지 않고 파이프라인이 "미해결" 행을 씁니다. 끝없이 재시도하지 않기 위한 규칙입니다. 분석에서는 실패로 세고 평가자에게는 보이지 않습니다. 네트워크나 로그인 문제로 인한 실패는 세지 않습니다.
  • 실행 시기가 다릅니다: Sonnet 전부와 Opus 대부분은 10월 18~19일에 돌았습니다. Fable은 11칸만 그때 돌았고 나머지는 10월 29일 이후입니다. 사용 한도와 장애 때문입니다.
  • 출력 길이 상한이 다릅니다: Fable은 64k, Sonnet과 Opus는 128k입니다. 도구의 기본값이고 우리가 정하지 않았습니다. 한계로 보고합니다.
  • 호출 방식: 계획서의 API 대신 Max 플랜의 Claude Code CLI를 썼습니다. 모델 버전은 claude-sonnet-5-5, claude-opus-5-5, claude-fable-5-1입니다.

  • 숨기는 것: 낸 모델과 푼 모델, 모델이 적은 근거와 어려운 이유, 중요한 이유, 신규성 자신감, 체커입니다.
